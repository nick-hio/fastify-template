# AGENTS.md

Guide for AI agents working in this repository. Humans should start with [README.md](README.md).

This is a template for HTTP APIs: Fastify 5 on the Bun runtime, SQLite through Drizzle ORM, Zod for validation, shipped as a Docker image. The `/example` route and its `kv` table are a working reference implementation. Copy their shape, then replace them.

## Commands

Run everything from the repository root.

| Command | What it does |
| --- | --- |
| `bun install` | Install dependencies |
| `bun run dev` | Start the server with reload on change (`NODE_ENV=development`, port 3000, database in `./data`) |
| `bun run check` | Typecheck, lint and test. **Run it before you report a change as done** |
| `bun test` | Tests only. `bun test test/example.test.ts` runs one file, `bun test -t "<name>"` runs matching tests |
| `bun run typecheck` | TypeScript only |
| `bun run lint` | Biome lint and format check, changes nothing |
| `bun run format` | Apply Biome formatting, import sorting and safe lint fixes |
| `bun run db:generate --name <change>` | Generate a migration from the schema files |
| `bun run db:backup [file]` | Copy the database to a file, safe while the server runs |
| `bun run start` | Start the server without reload |
| `docker compose up --build --wait` | Build the image, start it and wait until it is healthy |

## Layout

```
src/
├── index.ts          Process entrypoint: listens on the port, handles shutdown signals
├── server.ts         buildServer(): creates Fastify, registers plugins and routes
├── env.ts            Environment variables, validated with Zod
├── utils.ts          Small shared helpers
├── plugins/          Fastify plugins that apply to the whole server
├── routes/           One file per resource, registered in routes/index.ts
└── db/
    ├── index.ts      `db`, the Drizzle client
    ├── config.ts     Where the database file lives
    ├── backup.ts     `bun run db:backup`
    ├── schema/       One file per table, together with its Zod schemas
    ├── seeds/        Default rows per table, registered in seeds/index.ts
    ├── init/         Applies migrations and seeds when the server starts
    └── migrations/   Generated by drizzle-kit, never edited by hand
test/
├── setup.ts          Preloaded before the tests: points the run at a temporary database
├── helpers.ts        useServer(), useProcess() and shared test types
└── *.test.ts
```

## Conventions

### Routes

- Write each route file as a `FastifyPluginAsyncZod` and register it with a prefix in `src/routes/index.ts`.
- Give every route a Zod `schema` for each input it reads (`querystring`, `params`, `body`, `headers`) and for its success response. Fastify validates before the handler runs and types `req.query`, `req.params` and `req.body` from the schema, so handlers do not validate by hand.
- Responses are JSON. A response schema removes fields it does not list, and a response that does not match it becomes a 500.
- Answer 200 with the resource, 201 with the new resource after a create, and 204 with no body after a delete. Declare the schema under that status, as `src/routes/example.ts` does.
- Page a list by a cursor, not by an offset: accept `limit` and `cursor`, return `{ items, nextCursor }`. The list route in `src/routes/example.ts` is the reference.
- For an expected failure, throw an HTTP error from `@fastify/sensible`, for example `throw fastify.httpErrors.notFound("Entry Not Found")`.
- Let unexpected errors propagate. `src/plugins/error-handler.ts` logs them and answers with a generic 500, so do not wrap handlers in `try`/`catch` to do that yourself.
- Every error response has the body `{ statusCode, error, message }`. A request that fails validation is a 400 that also has `issues`, one `{ path, message }` per invalid field, such as `{ "path": "items.0.name", "message": "..." }`.
- Log with `req.log` inside handlers and `fastify.log` elsewhere, not `console`. Lint rejects `console`.
- Read the client address from `req.ip`. It is the address of the connection, or the one a proxy listed in `TRUST_PROXY` forwarded.
- A request that has no response after `REQUEST_TIMEOUT_MS` is answered with 503, and the handler keeps running. Pass `req.signal` to `fetch` and other calls that accept one, so they stop too. A route that needs longer sets its own `handlerTimeout`, in milliseconds, next to `schema`.

### Error handling

`safeAwait` and `safeTry` from `@/utils` return a failure instead of throwing it. The result is a tuple: `[null, data]` on success, `[error, null]` on failure.

```ts
const [error, response] = await safeAwait(fetch(url));

if (error) {
    req.log.warn({ err: error }, "Upstream request failed");
    throw fastify.httpErrors.badGateway("Upstream Unavailable");
}

// `response` is a `Response` from here on, not `Response | null`
```

- Pass a promise to `safeAwait` and a function to `safeTry`. `safeTry` is for synchronous code such as `safeTry(() => JSON.parse(text))`. It does not catch the rejection of an async function.
- Use them for a failure the code can act on: answer with a specific HTTP error, fall back to another value, or carry on without the result. Still use `try`/`catch` when handling large blocks of code or multiple failures together.
- Do not use them to turn an unexpected failure into a 500. Let it propagate, as described under Routes.
- Check `error` before you use `data`. Until then TypeScript types `data` as possibly `null`.
- Never drop the error, as in `const [, data] = await safeAwait(...)`. Handle it, log it or throw it again.
- `error` is always an `Error`. A thrown value that is not one, such as a string or `null`, is wrapped in an `Error` that keeps it as `cause`.
- Beyond that, `error` is typed without a runtime check. Narrow it with `instanceof` before relying on a specific class. To name another type, pass both type arguments: `safeTry<Config, SyntaxError>(...)`.

### Database

- Import the client as `import { db } from "@/db"`. It is one connection to a SQLite file, opened with Bun's built-in driver (`bun:sqlite`).
- Define one table per file in `src/db/schema/` and derive its Zod schemas there with `drizzle-orm/zod`. Routes reuse those schemas instead of redefining the shape.
- Keep the schema for a response apart from the schema for a request body. A client must not set what the database generates, such as `id` and `createdAt`, so the body schema lists the accepted fields with `.pick()`.
- Declare `.notNull()` on every column that needs a value, the primary key included. SQLite accepts `NULL` in a primary key that is not an integer.
- Store a timestamp as ISO 8601 text, like `createdAt` in `src/db/schema/kv.ts`. It is then a string in the database, in the handler and in the response.
- After changing a schema file, run `bun run db:generate --name <change>` and commit the new migration folder. Migrations are applied automatically when the server starts. `bun run check` fails while the schema files and the migrations disagree.
- Never edit or delete a migration that may already have been applied to a database. Add a new one.

Queries run synchronously inside the server process, so two of them never interleave.

- Outside a transaction, `await` a query as usual: `const rows = await db.select().from(kvTable)`.
- A transaction takes a synchronous callback. End each query in it with `.run()`, `.get()` or `.all()` instead of awaiting it, and throw to roll back:

    ```ts
    const entry = db.transaction((tx) => {
        const created = tx.insert(kvTable).values(values).returning().get();
        tx.insert(auditTable).values({ entryId: created.id }).run();

        return created;
    });
    ```

- Do the slow work, such as a `fetch` or hashing a password, before the transaction and pass the result in. TypeScript rejects an `async` callback, because the transaction would commit before the awaited work has finished.
- To answer 409 for a duplicate, insert with `.onConflictDoNothing().returning()` and throw `conflict` when no row comes back, as `POST /example` does. It is one statement, so it needs no transaction.
- Foreign keys are enforced, except while migrations run.

### Environment

- `src/env.ts` is the only file that reads `process.env`; lint rejects it anywhere else. Import `env` from `@/env`.
- When you add a variable, add it to `src/env.ts`, `.env.example` and the table in `README.md`. Add it to `compose.yml` too, as `NAME: ${NAME:-}`, or the container never sees the value.
- Validate a variable as what it is: `z.ipv4()` and `z.ipv6()` for an address, `z.url()` for a URL, `z.coerce.number()` for a number, `z.stringbool()` for a flag.
- Give a variable a default when it can have one. Without a default, nothing that imports `env` starts until the variable is set: set it in `test/setup.ts` and in `childEnv` of `test/helpers.ts` for the tests, and under `env` of the `docker` job in `.github/workflows/ci.yml`.

### Code style

- Biome owns formatting and import order. Run `bun run format` rather than formatting by hand.
- Import from `src/` through the `@/` alias, without a file extension. Use the `node:` prefix for built-in modules.
- Cross-cutting behaviour belongs in a plugin in `src/plugins/`, wrapped with `fastify-plugin` and registered in `src/server.ts` before the routes.

### Tests

- Tests run against a real server and a real, temporary SQLite database. Nothing is mocked, and `./data` is never touched.
- Call `useServer()` from `test/helpers.ts` in a `describe` block, then send requests with `server().inject()`.
- For what only exists in a running process, such as a signal, a timeout or a variable read at startup, call `useProcess()` instead. It starts `src/index.ts` as its own process, with the defaults of `src/env.ts` and the environment variables you pass. `test/process.test.ts` shows how.
- Tests in a run share one database, so empty the tables a file uses in `beforeEach`.
- Type response bodies explicitly, as in `response.json<KvEntry>()`. An untyped `response.json()` inside `expect()` fails the typecheck.
- Add or update tests in the same change as the behaviour they cover.

## Things that will trip you up

- **Library versions are newer than most documentation.** This project uses Drizzle ORM 1.0 (release candidate), Zod 4 and TypeScript 7. Their APIs differ from Drizzle 0.x and Zod 3, for example `drizzle-orm/zod` replaces the `drizzle-zod` package. When unsure, read the types in `node_modules` instead of relying on memory.
- **New package versions can be refused.** `bunfig.toml` only installs versions published at least 3 days ago. If `bun add` cannot resolve a brand-new release, pin the previous version. Do not remove the setting.
- **`.dockerignore` is an allowlist and the image copies only `src/`.** A new top-level file or directory that the server needs at runtime must be added to `.dockerignore` and copied in the `release` stage of the `Dockerfile`.
- **The container can only write to `/data`.** `compose.yml` mounts the root filesystem read-only. Write persistent files under `DATA_DIR`.
- **Seeds only fill empty tables.** Changing a seed does not change a database that already has rows in that table. Use a migration for that.
- **A generated migration can fail on a table that has rows.** The tests only apply migrations to an empty database. Read the SQL of every migration, as [change-schema](.agents/skills/change-schema/SKILL.md) describes.
- **The database is three files.** Next to `database.db`, SQLite keeps `database.db-wal` and `database.db-shm` while the server runs. Copy the database with `bun run db:backup`, never with `cp`.
- **Some Node.js server options do nothing under Bun.** `requestTimeout` is one of them. Check that an option has an effect before relying on it.
- **Compose mounts a host directory.** `compose.yml` binds `DATA_DIR` (default `./data`) to `/data`. The directory must exist and belong to the user the container runs as, see [docker-image](.agents/skills/docker-image/SKILL.md).
